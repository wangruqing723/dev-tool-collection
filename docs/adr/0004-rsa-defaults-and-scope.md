# RSA 默认填充的刻意不对称，以及不做混合加密

RSA 加解密默认 OAEP + SHA-256，而签名默认 PKCS1v1.5 + SHA-256（即 `SHA256withRSA`）。两侧默认填充不一致是刻意的：加密侧的 PKCS1v1.5 有 Bleichenbacher 类攻击史，不宜作默认；签名侧的现实生态（支付宝 RSA2、微信支付、银联）几乎清一色是 PKCS1v1.5，若默认 PSS，多数用户第一次验签就会失败。两侧都保留另一种填充以供对接。

同时明确不做混合加密。RSA 单次明文上限受填充开销限制（2048 位密钥下 OAEP/SHA-256 为 190 字节、OAEP/SHA-1 为 214、PKCS1v1.5 为 245），超限时前置校验并报出可读错误，而不是自动降级为「RSA 加密随机 AES 密钥 + AES 加密正文」。混合加密的封装格式属协议级决策，自造一种只会产出除本工具外无人能解的密文，是假的可用性。

## PKCS#1 v1.5 只在加密方向可用

实现时发现一处运行时约束：Node 18.19+ / 20+ 已禁用 PKCS#1 v1.5 的**私钥解密**（CVE-2023-46809，Marvin 攻击），仅能通过 `--security-revert` 启动参数恢复，而 Raycast 的运行时不由我们控制。公钥加密方向不受影响。

因此 PKCS#1 v1.5 成为单向能力：可用于给只认它的老系统投递密文，但无法解开这类密文。UI 上该选项只在「加密」时列出，「解密」时改为提示改用 openssl。签名验签走的是另一套 API，不受此约束，PKCS#1 v1.5 仍是签名默认值。

## Consequences

「为什么签名和加密的默认填充不一样」会被反复问起，答案在本文。若要改动任一默认值，请注意它会静默改变已有用户的互操作结果。

`rsa.test.ts` 中有一条测试直接断言 Node 仍拒绝 PKCS#1 v1.5 私钥解密。若将来 Node 改变行为，该测试会失败，届时应重新审视此处的单向限制。
